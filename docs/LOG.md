## 2026-08-08

**스택을 Hugo 로 확정했다. 이유가 속도가 아니라 "영구 비용" 으로 바뀌었다.**

처음엔 기준 다섯 개를 표로 놓고 넷에서 앞선다는 식으로 봤는데, 확정 직전에 다시 보니
그 셈이 별로 중요하지 않았다. 진짜 갈림길은 **비용이 언제 청구되느냐**였다.
Go 템플릿은 뼈대 짤 때 한 번 내고 끝나는 값이고, Node 생태계는 글을 쓰러 올 때마다
조금씩 나오는 값이다. 총량은 앞이 크지만 **글쓰기를 막는 건 뒤쪽**이다.
이 블로그의 병목이 방문자가 아니라 쓰는 사람의 지속성이라는 걸 인정하니 답이 하나였다.

**Zola 를 아예 빠뜨리고 검토했었다.**

Rust 단일 바이너리에 Tera 템플릿이라, Hugo 에 대한 유일한 불만(Go 템플릿)을
정확히 겨냥한 물건이다. 후보 표에 없었던 게 그냥 누락이었다.
탈락시키긴 했지만 이유가 "몰라서" 가 아니라 **대중성 5배 차이** 로 바뀐 건 큰 차이다.
검토를 안 한 채로 내린 결정과 하고 내린 결정은 나중에 흔들릴 때 값이 다르다.

**"방치하면 Node 가 깨진다" 는 통념은 과장인데, 비용은 다른 자리에 진짜로 있었다.**

락파일과 Node 버전을 고정하면 `npm ci` 는 몇 년 뒤에도 같은 걸 재현한다. 빌드는 안 깨진다.
그런데 **Astro 6 이 2026-03-10 에 나오면서 Node 18·20 지원을 끊었다.**
2024년에 시작한 사람은 지금 Astro 만이 아니라 런타임까지 올려야 한다.
빌드 실패가 아니라 **"글 쓰러 왔다가 업그레이드 가이드를 읽고 있는 상태"** 가 비용이었다.
막연한 불안을 날짜가 분명한 사건으로 바꿔놓으니 판단이 쉬워졌다.

**Hugo 자료 대부분이 낡았다. 0.146 에서 템플릿 구조가 통째로 바뀌었다.**

`layouts/_default/` 가 사라지고 페이지 종류 ↔ 템플릿이 1:1 이 됐다.
파샬 경로에는 밑줄이 붙어 `layouts/_partials/` 가 됐고, 렌더 훅도 `layouts/_markup/` 으로 옮겼다.
하위 호환이 있어서 옛 구조도 "되기는 한다" 는 게 고약하다 — 안 되면 바로 알 텐데,
되니까 낡은 구조를 그대로 안고 가다가 나중에 검색한 답과 내 디렉터리가 안 맞는다.
그래서 기억으로 짜지 않고 `hugo new theme` 가 만드는 구조를 먼저 확인하고 갔다.
**전에 슬래시 하나에 걸렸던 것과 같은 계열이다. 조용히 틀리는 쪽이 늘 비싸다.**

**시안을 대문에 덮지 않고 `/sample/` 아래에 얹었다.**

`index.html` 은 손대지 않고 링크 한 줄만 넣었다. 1차 때 "변수를 하나로 줄인다" 로
스택을 미뤘던 것과 같은 판단이다. 시안이 마음에 안 들어 엎어도 대문은 멀쩡하고,
지울 것도 링크 한 줄뿐이다. 루트는 시안을 눈으로 확인한 뒤에 넘긴다.
`favicon.svg` 가 잠깐 두 벌(루트와 `static/`)이 되는데, 루트를 넘기는 시점에
루트 사본을 지우면 `static/` 쪽만 남는다. **중복이 옳은 방향으로 풀린다.**

**§6 에 적어둔 "한글 슬러그" 는 스택 문제가 아니었다.**

Hugo·Astro·Zola 셋 다 한글을 로마자로 바꿔주지 않는다. 그대로 URL 에 넣어
퍼센트 인코딩되고, 답은 셋 다 "front matter 에 `slug` 를 직접 적는다" 로 같다.
**스택이 정해져야 알 수 있다고 생각해서 미뤄뒀는데, 미룰 이유가 없던 항목이었다.**
반대로 **글 URL 규칙은 여전히 안 정했다.** 시안이 Hugo 기본값을 쓰고 있을 뿐이고,
못 바꾸는 결정이라 대문을 옮기기 전에 따로 정해야 한다. 기본값에 떠밀려 정해지면 안 된다.

## 2026-08-07

**파비콘을 profile-site 것으로 바꿨다. 모양도 색도 같다.**

처음에 직접 그린 `E` 대신 `elkiss.me` 파비콘을 가져왔다. 세로 기둥에 가로 세 줄,
가운데만 짧은 블록 글자다. 직접 그린 것보다 글자로 확실히 읽힌다.

**두 사이트가 같은 아이콘을 써도 손해가 거의 없다.** 탭에 둘 다 띄우면 구분이
안 되지만, 그렇게 여는 사람은 사실상 만든 사람뿐이다. 방문자는 프로필에서 블로그로
한 번 넘어갈 뿐 둘을 동시에 열어두지 않는다.

붉은 면으로 갈라보는 안을 검토했다가 접었다. 색을 파비콘에만 쓰면 사이트 안엔
붉은 게 하나도 없는데 탭만 붉어서 **왜 붉은지 설명이 안 된다.** 붉은색을 쓰려면
사이트 강조색으로 같이 가야 하는데, 그건 파비콘 고르다 곁다리로 정할 일이 아니다.
그래서 공사중 표지의 머스터드(`--sign`)도 그대로 뒀다. 표지판에만 쓰는 색이라
사이트 강조색으로 승격하지 않는다.

**profile-site 는 data URI, 여기는 파일로 둔다.** 같은 그림인데 방식이 다르다.
프로필은 영원히 한 장이라 HTML 안에 넣는 쪽이 외부 요청 0을 지킨다.
블로그는 목록·본문·소개로 페이지가 늘어나는데, data URI 는 **페이지마다 같은
문자열이 HTML 에 실려 오는** 반면 파일은 브라우저가 한 번 받아 캐시한다.

**배포를 기본 방식에서 커스텀 Actions 로 바꿨다.** profile-site 에서 먼저 겪고 옮긴 것이다.

기본 방식(`Deploy from a branch`)은 **저장소 루트를 통째로 올린다.** 그러면
`blog.elkiss.me/docs/LOG.md` 로 이 문서가 열리고, Jekyll 이 자동으로 돌면서
마크다운을 읽기 좋은 HTML 로 렌더링까지 해준다. public 저장소라 유출은 아니지만
**작업 문서가 개인 도메인에서 서비스되고 검색엔진에 색인될 이유는 없다.**
문서가 앞으로 계속 쌓이는 블로그라 profile-site 보다 이 문제가 크다.

워크플로에서 `_site` 에 **필요한 파일만 골라 담는다.** 지금은 `index.html`,
`favicon.svg`, `CNAME` 셋이다. `CNAME` 을 빼먹으면 커스텀 도메인이 풀린다.
`concurrency` 로 진행 중인 배포를 취소하게 해뒀는데, 연달아 푸시했을 때
배포가 줄줄이 대기하며 꼬이는 것을 막기 위해서다.

**스택을 얹을 때 이 구조가 그대로 쓰인다.** `Assemble site` 단계만 빌드 명령으로
바꾸면 되고 나머지는 손댈 게 없다. 지금 옮겨두면 그때 인프라와 빌드를 동시에
의심할 일이 없어진다.

**슬래시 하나에 걸렸다.** `href="/favicon.svg"` 로 적었더니 배포본에서는 맞는데
`file://` 로 연 로컬 미리보기에서 안 떴다. 맨 앞 슬래시는 사이트 루트를 뜻해서
로컬에서는 드라이브가 아니라 파일시스템 최상단을 찾아간다.
고약한 건 **에러가 안 난다**는 점이다. 아이콘이 조용히 비어 있을 뿐이라 파일이
잘못됐나 캐시인가 배포가 안 됐나 엉뚱한 데를 뒤지게 된다.
실제로 이때 원인이 둘이었다 — 경로가 하나, 아직 push 를 안 한 게 하나.

## 2026-08-05

**인프라가 붙었다.** 원격 저장소를 만들고 Pages 를 켜고 커스텀 도메인을 넣었다.
`nslookup` 으로 보니 `blog.elkiss.me` 가 `elkiss87.github.io` 를 거쳐
`185.199.108~111.153` + IPv6 4개로 풀렸고, HTTPS 도 200 으로 응답했다.
**서브도메인은 apex 보다 훨씬 빨랐다.** flattening 도 A 레코드 8줄도 없이 CNAME 하나였다.

**예고한 함정에 그대로 걸렸다.** Pages 에 커스텀 도메인을 저장하면 GitHub 이
원격 저장소에 `CNAME` 파일을 **자기가 커밋한다.** 로컬은 그걸 모르니
`ahead 1, behind 1` 로 갈라진다. `git pull --rebase` 로 GitHub 커밋 위에 얹어서 풀었다.
막힌 건 아니지만 모르고 만나면 첫 push 가 거부당해서 당황할 자리다.

**사이트를 열었더니 README 가 떴다.** 저장소에 `index.html` 이 없으면
**Pages 가 Jekyll 을 돌려 `README.md` 를 기본 테마로 렌더링한다.**
Jekyll 을 쓰겠다고 한 적이 없는데 기본 동작이 그렇다. 응답 HTML 에 `Jekyll SEO tag`
주석이 남아 있어서 알았다. 인프라가 정상이라는 신호이기도 했다 — 도메인·인증서·서빙이
다 도는데 보여줄 파일만 없던 것이다.

**공사중 페이지를 만들었다.** 워드마크는 `ELKISS BLOG` 대문자에 자간 `.16em` 으로
profile-site 와 맞췄다. 표지판은 인라인 SVG 다. 이모지는 플랫폼마다 다르게 그려지고
이미지 파일은 외부 요청이 늘어서 둘 다 안 썼다.
푸터의 `elkiss.me` 만 대문자 변환에서 뺐다. **도메인은 주소라 소문자가 원래 모양이다.**

**favicon 과 소셜 미리보기를 넣었다.** favicon 은 크기별 png 를 여러 장 두는 오래된
관례 대신 **SVG 한 장**으로 갔다. 요즘 브라우저는 해상도에 맞춰 알아서 그린다.
그림은 워드마크가 아니라 머리글자 `E` 하나다 — 탭에서 16px 로 줄어들면 글자 여러 개는
뭉개진다. 선으로 그리지 않고 **면으로 채운 사각형에 흰 글자**를 얹은 것도 같은 이유다.

**`og:image` 는 일부러 비웠다.** 지금 화면은 공사중이라 미리보기로 걸어두면
글이 생긴 뒤에도 그 이미지가 캐시로 남는다. 슬랙·카톡은 한 번 받은 미리보기를 오래 들고
있어서 고쳐도 잘 안 바뀐다. **없는 편이 틀린 것보다 낫다.**

## 2026-08-04

저장소를 열고 방향을 잡았다. 아직 아무것도 배포되지 않았다.

**스택을 정하려다 멈췄다.** Hugo·Astro·11ty·Jekyll 을 비교해 [STACK.md](STACK.md) 에
정리했고 Hugo 쪽으로 기울었지만, **확정하지 않고 1차 목표에서 빼기로 했다.**
스택을 얹은 채로 사이트가 안 뜨면 DNS·빌드·Actions 중 무엇이 원인인지 구분이 안 된다.
`index.html` 하나면 안 뜰 때 원인이 인프라밖에 없다. profile-site 때와 같은 판단이다.

**검토하면서 처음 전제가 틀렸다는 걸 알았다.** 갈림길을 "빌드를 로컬에서 하느냐
서버에서 하느냐" 로 봤는데, GitHub Actions 가 그걸 흡수해서 어느 도구든 똑같았다.
남는 진짜 기준은 **로컬 미리보기**였다. 폭·줄간격·코드 블록을 보면서 고쳐야 하는데,
로컬에서 못 띄우면 push 하고 기다려 확인하기를 반복하게 된다.

**판단 기준에 "방치 내성" 을 넣었다.** 개인 블로그는 반드시 몇 달 방치된다.
그때 돌아와서 글을 쓰는 게 아니라 빌드를 고치고 있으면 안 된다.
이 기준 하나가 Node 계열(Astro·11ty)과 단일 바이너리(Hugo)를 가른다.

**색은 `elkiss.me` 와 같은 값으로 잡았다.** 서브도메인이라 오가는 사람이 같은 곳으로
느껴야 한다. 폭만 400px → 640px 로 넓혔다. 프로필은 링크를 누르는 곳이고 여기는 읽는 곳이다.

**"모바일 우선" 을 걷어냈다.** profile-site 에서 그대로 가져온 문구였는데,
거기는 인스타그램에서 눌러 들어오는 모바일이 실제 방문자라 맞는 말이었다.
블로그는 앉아서 읽고 이력서 링크로도 열린다. **양쪽 다 깔끔한 것**이 목표다.
`CLAUDE.md` 부터 문서 전체에서 고쳤다. 원칙 문구 하나가 나중에 레이아웃 판단을
전부 끌고 가기 때문에, 틀린 채로 두면 그 위에 쌓은 결정이 같이 틀어진다.

**CNAME flattening.** apex 는 NS·SOA 가 있어야 해서 CNAME 을 못 건다.
그런데 Pages 의 IP 는 고정 약속이 아니라 A 레코드로 고정하면 GitHub 이 인프라를 바꾸는 날
사이트가 조용히 죽는다. Cloudflare 는 설정만 CNAME 으로 받고 밖에는 A 로 답해서 이 사이를
메운다. `blog.` 는 서브도메인이라 이 얘기가 아예 해당 없고 CNAME 하나면 된다.
