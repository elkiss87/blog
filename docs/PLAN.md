## 1. 1차 목표 — 인프라

> **`https://blog.elkiss.me` 를 열면 "Hello, world." 가 뜬다.**

**스택은 이 단계에서 정하지 않는다.** `index.html` 파일 하나로 간다.

profile-site 때와 같은 이유다 — **변수를 하나로 줄인다.**
Hugo 든 Astro 든 얹은 상태에서 사이트가 안 뜨면 DNS 문제인지 빌드 문제인지
Actions 문제인지 구분이 안 된다. HTML 하나면 안 뜰 때 원인이 인프라밖에 없다.

도메인·DNS·HTTPS 는 profile-site 에서 한 번 겪었지만 **같은 절차가 아니다.**
그때는 apex(`elkiss.me`)였고 이번은 서브도메인이다. 확인해야 할 것이 남아 있다.

## 5. 사이트 규칙

고칠 때마다 다시 정하지 않도록 적어둔다. **정해진 만큼만 적는다.**

### 페이지는 셋으로 시작한다

**글 목록 / 글 본문 / 소개.** 이것보다 늘리지 않는다.

- 첫 화면은 **글 목록**이다. 프로필은 `elkiss.me` 가 이미 한다.
  블로그 첫 화면까지 자기소개로 쓰면 같은 말을 두 번 하게 된다
- **소개 페이지는 짧게.** 여기서 뭘 읽을 수 있는지와 프로필 링크까지다
- 태그·아카이브·시리즈는 **글이 쌓여서 목록이 안 읽힐 때** 만든다. 지금은 아니다

`/about/` 은 `content/about.md` 하나다. `content/posts/` 밖이라 목록·RSS 에서 빠지고,
front matter 에 `date` 를 안 적어서 날짜도 안 붙는다 — **글이 아니라 페이지다.**
이전/다음 링크는 `posts` 섹션에서만 그린다. 최상위 페이지에 붙이면 소개와 시안이
서로를 이전 글로 가리키는데, 둘은 이어지는 글이 아니다.

### 글감의 범위 — 2026-08-11 시점에 **확정하지 않았다**

글이 한 편도 없는 상태에서 "내가 앞으로 뭘 쓸 사람인가" 를 정하면 증거 없이 정하는 것이다.
다섯 편쯤 쌓이면 저절로 드러난다. **그때 다시 본다.**

**그때 볼 것 1순위는 소개의 예시 세 줄이다.** 소개에서 제일 빨리 낡는 부분이라서다 —
태도를 적은 문장은 안 낡지만 예시는 글이 쌓이면 실제 글과 어긋난다.
지금 세 줄(도메인·팬그램·모바일)은 **실제로 있었던 질문**이라 맞다.
없는 걸 약속하지 않는 것이 넓어 보이는 것보다 낫다.

- **개발 중심으로 열되 소개에서 닫지 않는다.** 소개의 "거기에만 묶어두지는 않습니다"
  한 문장이 그 일을 한다. 읽는 사람에겐 개발 블로그로 보이고 쓰는 사람은 안 막힌다
- 비대칭이 있어서 이렇게 정했다. **넓게 두고 좁히기는 쉽고**(안 쓰면 된다),
  **좁게 선언하고 넓히기는 어색하다**(소개를 고쳐야 하고, 안 고치면 쓰고 싶은 걸 못 쓴다)
- 소개 문단은 **되돌리는 값이 싼 결정**이다. 파일 하나다. 글 주소를 시안 확인보다
  먼저 닫은 것과 정확히 반대 경우라, 지금 완벽하게 정할 이유가 없다

**알고 감수하는 비용**

- 주제가 넓어지면 **이력서 링크로서의 신호가 흐려진다.** PLAN 은 이 사이트를
  이력서에 걸 링크로 본다. 실제로 부딪히면 그때 분류를 만든다
- 주제마다 **틀렸을 때의 무게가 다르다.** 팬그램이 틀리면 그냥 틀린 것이지만
  과학·투자 쪽은 읽는 사람이 판단에 쓴다. 겪지 않고 찾아본 글은 **출처를 남긴다**
- 회사 이야기는 일반화한다 → `CLAUDE.md`. 이 규칙은 범위가 넓어져도 그대로다

**소개에 방법론을 쓰지 않기로 했다.** AI 와 함께 알아본다는 것을 소개에 선언하는 안을
검토했다가 뺐다. 소개는 *"여기서 뭘 읽을 수 있는가"* 를 말하는 자리고, 읽는 사람이 얻는 것은
의문과 답이지 그것을 누구와 만들었는지가 아니다. **말할 것이 아니라 글에서 출처로 보여줄 것.**

### 글

- **날짜를 적는다.** 기술 글은 언제 쓴 것인지가 내용의 일부다
- **분량으로 글을 나누지 않는다.** 한 편에 하나의 이야기가 끝나면 그게 한 편이다
- 회사 이야기는 **일반화해서** 쓴다. 회사를 지우고도 남는 것이 글감이다 → `CLAUDE.md`

### 글 주소 — 2026-08-08 확정

> **`blog.elkiss.me/<파일명>/`**

| | |
|---|---|
| 파일 | `content/posts/<파일명>.md` |
| 주소 | `blog.elkiss.me/<파일명>/` |
| 설정 | `hugo.toml` 의 `[permalinks] posts = '/:contentbasename/'` |

**파일명이 곧 주소다.** 영문 소문자와 하이픈만 쓰고, 제목 번역이 아니라 주제 요약으로
두세 단어. 블로그 전체에서 유일해야 한다. 제목은 한글로 자유롭게 쓴다.

- **번호를 붙이지 않는다.** 순서는 `date` 로 계산되는 값이지 저장할 값이 아니다.
  날짜를 소급해 한 편 끼워 넣으면 뒤 글의 번호가 전부 밀리는데, 그때 다시 매기면
  주소가 깨지고 안 매기면 번호가 거짓말이 된다. **관리할 대상 자체를 만들지 않는다**
- **날짜를 주소에 넣지 않는다.** 고쳐 쓰는 기술 글에서 주소의 날짜는 곧 거짓이 된다.
  날짜는 본문에 표시하고 정렬·RSS 에 쓴다
- **`slug` 를 쓰지 않는다.** `:contentbasename` 은 front matter 의 `slug` 를 무시한다.
  적어두면 안 먹는데 먹는 줄 알게 되니 아예 안 쓴다
- **제목을 고쳐도 주소는 그대로 둔다.** 파일명을 안 건드리면 된다
- 폴더는 `content/posts/` 를 유지하되 주소에는 안 나온다.
  파일 정리와 주소를 분리해두면 나중에 폴더를 나눠도 주소가 안 깨진다

**최상위에 예약된 이름** — 글 파일명으로 쓰면 안 된다.

```
about  posts  tags  categories  page  search  css  pangram
index  index.xml  sitemap.xml  robots.txt  404.html  favicon.svg  CNAME
```

`posts` 는 글 주소를 평평하게 해도 **섹션 목록 페이지로 남는다.** 아카이브가 공짜로 딸려온다.
`page` 는 페이지네이션(`/page/2/`)이 쓴다. 겹치면 Hugo 가 빌드할 때 잡아준다.

### 시안 문서는 글이 아니다

`content/pangram.md` 는 발행할 글이 아니라 **레이아웃을 재는 자다.**
`content/posts/` 밖에 두고 목록·RSS·sitemap 에서 뺐다. 주소(`/pangram/`)로는 열린다.
CSS 를 고칠 때마다 다시 열어보는 용도라 남겨둔다.

### 화면 — 한쪽을 우선하지 않는다

profile-site 는 인스타그램에서 눌러 들어오는 모바일이 실제 방문자라 모바일 우선이 맞았다.
**블로그는 다르다.** 기술 글은 앉아서 읽고, 이력서에 걸 링크라 데스크톱으로 열릴 일도 많다.
어느 쪽도 "되기는 한다" 수준으로 두지 않는다.

- **글 본문의 가독성이 최우선이다.** 폭·줄간격·글자 크기를 먼저 맞춘다.
  한글 본문은 한 줄이 너무 길면 눈이 다음 줄을 놓친다. 데스크톱에서 폭을 제한하는 이유가
  화면이 남아서가 아니라 **길면 읽기 나쁘기 때문**이다
- **코드 블록을 양쪽에서 확인한다.** 기술 블로그에서 제일 자주 깨지는 자리다.
  모바일에서는 가로 스크롤이 본문을 밀지 않아야 하고, 데스크톱에서는 줄바꿈이
  코드를 망가뜨리지 않아야 한다
- 고칠 때는 **좁은 폭과 넓은 폭을 같이 본다.** 한쪽만 보고 고치면 반드시 다른 쪽이 깨진다
- 자바스크립트가 없어도 글은 읽혀야 한다

### 본문 폭 — 2026-08-11 확정

> **데스크톱 720px (800px 이상에서), 그 아래는 640px**

한 줄에 한글 40자다. 라틴은 45~75자가 권장 범위지만 **한글은 25~40자**다.
음절 블록이 전각이라 자리를 두 배 먹고 담는 정보량도 많아서 그대로 옮겨오면 안 된다.

**폭과 글자 크기는 묶여 있다.** 720px 이 읽기 좋은 것은 본문이 17px 이기 때문이고,
18px 로 키우면 38자, 16px 로 줄이면 42자가 된다. **둘 중 하나를 건드리면 다른 쪽도 같이 본다.**

### 코드 블록 — 스크롤로 둔다

넘칠 때 **상자 안에서만** 가로로 밀리고 본문을 밀지 않는다. 접지 않는다 —
코드는 줄바꿈 위치가 의미다. 업계 기본값이기도 하다.

본문 밖으로 넓히는 방식(코드만 좌우로 삐져나가게)은 **검토했고 미뤘다.**
시안 문서 47줄 중 데스크톱에서 넘치는 진짜 코드가 1줄이라, 그 하나를 위해
브레이크포인트를 하나 더 관리할 값어치가 없었다. 모바일에서 7줄이 넘치는 것은
설계대로다 — 297px 상자에 코드가 들어올 리 없고, 봐야 할 것은 본문이 안 밀리는지다.

실제 글에 긴 템플릿 타입이나 로그 출력이 들어와 거슬리면 그때 켠다.
CSS 다섯 줄이고 **나중에 넣어도 값이 안 올라간다.**

### 다크모드 — 2026-08-11 확정

> **OS 설정을 따르고, 헤더 토글로 덮어쓴다.**

색은 `elkiss.me` 와 같은 값이다. 검정이 아니라 따뜻한 쪽으로 내린다 —
라이트가 순백이 아닌 미색이라 중성 회색으로 가면 짝이 안 맞는다.

| | 라이트 | 다크 |
|---|---|---|
| `--bg` | `#faf9f7` | `#141412` |
| `--text` | `#1c1c1a` | `#f2f0eb` |
| `--text-sub` | `#6b6a66` | `#97948d` |
| `--line` | `#e5e3de` | `#302f2b` |
| `--code-bg` | `#f3f1ed` | `#1c1b19` |

- **토글은 2단계다.** 고른 값이 OS 설정과 같아지면 저장값을 지워서
  "시스템 따라가기" 로 돌아온다. 버튼을 셋으로 늘리지 않고 되돌릴 수 있다
- **`elkiss.me` 는 토글이 없다.** 5초 머무는 링크 페이지와 긴 글을 읽는 곳은 다르다
- 자바스크립트가 없으면 버튼이 안 보이고 **OS 설정대로 읽힌다.** 글은 그대로다

## 6. 앞으로 할 것

**언제 하느냐로 나눈다.** 지금 필요한 것과 글이 쌓여야 뜻이 생기는 것은 다르다.
필요해지기 전에 만들면 쓰지도 않는 것을 유지하게 된다.

### 다음 — 이미지 (2026-08-15~)

글에 그림을 넣을 수 있게 한다. 첫 글에 넣을 그림이 준비되면서 필요해졌다.

- **렌더 훅으로 처리한다.** 마크다운의 `![대체 텍스트](경로 "캡션")` 을 가로채
  `<figure>` + `<figcaption>` 으로 내보낸다. 제목이 없으면 그냥 `<img>` 다.
  숏코드를 쓰지 않는 이유는 **마크다운을 평범한 채로 두기 위해서**다 —
  나중에 스택을 옮겨도 글이 안 깨진다
- `loading="lazy"` 를 자동으로 붙인다
- **다크모드 대비가 제일 큰 문제다.** 배경이 `#faf9f7` 과 `#141412` 둘이라
  흰 배경 그림은 어두운 화면에서 판이 번쩍인다. 투명 배경 선화를 우선하고,
  안 되면 테두리를 둘러 "삽화 판" 으로 읽히게 한다
- 파일은 `static/images/` 에 둔다. 한 장뿐이라 페이지 번들은 아직 이르다.
  이미지가 글마다 붙기 시작하면 그때 번들로 옮긴다 (주소는 안 바뀐다)
- **시안 문서에 그림 칸을 만든다.** 각주 때와 같은 이유다 —
  자에 없는 것은 다음에 재지 못하고 지나간다
- `og:image` 를 정한다. 지금은 일부러 비워둔 상태다 → [LOG.md](LOG.md) 2026-08-05.
  진짜 글이 생겼으므로 글마다 대표 이미지를 줄지 결정할 때가 됐다

### 작은 것 — 필요하면 곁다리로

- **제목 앵커** — `h2` 에 `#` 링크를 붙여 특정 대목을 가리킬 수 있게 한다.
  절이 여덟 개쯤 되는 글에서 쓸모가 있다
- **목차(TOC)** — `hugo.toml` 에 `[markup.tableOfContents]` 설정만 있고 그리지 않는다.
  긴 글이 나오면 켠다. 짧은 글에 목차는 오히려 방해다

### 글이 쌓이면

- **분류(태그)** — 목록이 안 읽힐 때 만든다 (§5). 지금 만들면 빈 태그 페이지만 생긴다.
  분류의 축은 §5 "글감의 범위" 를 다시 볼 때 같이 정한다
- **아카이브** — 연도별 목록. 태그와 같은 시점
- **검색** — 글이 스무 편은 넘어야 뜻이 있다. 정적 사이트라 색인을 빌드 때 만들고
  브라우저에서 찾는 방식이 된다. 자바스크립트가 처음으로 무거워지는 자리다

### 읽는 사람이 생기면

- **공유 버튼** — 신중하게. 대개 추적기가 딸려온다
- **방문자 분석**

### 구현이 막히면

**설치하지 말고 읽는다** → [STACK.md](STACK.md). 널리 쓰이는 테마의 소스를 읽어
구조를 참고하되, 코드를 그대로 가져오지 않는다. 라이선스 표시 의무가 따라붙고,
남의 마크업을 물려받지 않기로 한 결정과도 어긋난다.

### 안 하기로 한 것

**댓글은 달지 않는다** (2026-08-16).

정적 사이트라 댓글은 외부 서비스를 붙여야만 가능하고, 그러면 **외부 요청 0 이 깨진다.**
대개 계정과 추적기가 함께 딸려온다. 읽는 사람이 많지 않은 동안에는
얻는 것보다 스팸을 걸러내는 품이 크다.

**GitHub 기여 그래프(잔디)는 넣지 않는다** (2026-08-12). 다시 떠오를 아이디어라 적어둔다.

- **정적 사이트라 낡는다.** push 할 때만 다시 빌드되므로 배포 사이의 잔디는 옛 것이다.
  활동 그래프가 낡은 것은 없는 것보다 나쁘다 — 보는 사람은 오늘 상태로 읽는다.
  최신으로 두려면 장식 하나 때문에 매일 도는 빌드를 만들어야 한다
- **실제 작업량을 저평가한다.** 글쓴이의 회사 일은 GitHub 에 찍히지 않는다.
  빈 잔디가 사실을 반대로 말한다
- **첫 화면은 글 목록이다** (§5). 잔디는 자기소개고, 그건 `elkiss.me` 가 이미 한다
- 넣는다면 대문이 아니라 소개 페이지이고, 외부 서비스가 아니라 빌드 때 인라인 SVG 로
  구워야 한다. 이 사이트는 외부 요청이 0이다

꾸준함을 보여주는 것이 목적이라면 **글 목록이 잔디보다 낫다.** 잔디는 "얼마나 많이" 를,
글 목록은 "무엇을" 을 보여준다.

지금 정할 필요가 없는 것을 미리 정하지 않는다.
