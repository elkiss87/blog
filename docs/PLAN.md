작성 시작: 2026-08-04

**모바일과 데스크톱 양쪽에서 깔끔해야 한다.** 한쪽을 우선하지 않는다.

## 1. 1차 목표 — 인프라

> **`https://blog.elkiss.me` 를 열면 "Hello, world." 가 뜬다.**

**스택은 이 단계에서 정하지 않는다.** `index.html` 파일 하나로 간다.

profile-site 때와 같은 이유다 — **변수를 하나로 줄인다.**
Hugo 든 Astro 든 얹은 상태에서 사이트가 안 뜨면 DNS 문제인지 빌드 문제인지
Actions 문제인지 구분이 안 된다. HTML 하나면 안 뜰 때 원인이 인프라밖에 없다.

도메인·DNS·HTTPS 는 profile-site 에서 한 번 겪었지만 **같은 절차가 아니다.**
그때는 apex(`elkiss.me`)였고 이번은 서브도메인이다. 확인해야 할 것이 남아 있다.

**완료 조건**

- [x] 원격 저장소 `elkiss87/blog` (public) + `origin` 연결
- [x] `blog.elkiss.me` DNS 연결 — CNAME 하나, DNS only
- [x] HTTPS — 인증서 발급 완료, 200 응답 확인
- [x] GitHub Pages 가 저장소 내용을 서빙한다
- [x] `index.html` 이 실제로 보인다
- [x] 과정을 [LOG.md](LOG.md) 에 남긴다 — 첫 글의 재료다

**2026-08-05 달성.** 이제부터는 파일만 고치면 되고, 인프라는 다시 건드리지 않는다.

디자인은 이 단계에서 완성하지 않는다. **경로가 먼저다.**

## 2. 2차 목표 — 글을 쓰는 경로

> **마크다운 파일을 하나 추가하고 push 하면 목록과 본문이 알아서 생긴다.**

여기서 스택을 고른다 → [STACK.md](STACK.md).
1차가 끝나 인프라가 의심 대상에서 빠진 다음이라야 빌드 문제를 빌드 문제로 볼 수 있다.

**첫 글은 1차 목표를 하면서 겪은 것으로 쓴다.** 그래서 [LOG.md](LOG.md) 를
지금부터 남긴다. 막힌 지점과 잘못 짚은 것이 글의 알맹이인데, 그건 겪는 순간에만 남는다.

## 3. 현재 상태

| 항목 | 상태 |
|---|---|
| 원격 저장소 | `elkiss87/blog` (public), `origin` 연결됨 |
| 커밋 이메일 | `user.email` 을 noreply 주소로 로컬 설정 완료 |
| 대문 | `index.html` — 공사중 한 장. 배포됨. **Hugo 가 건드리지 않는다** |
| 시안 | `/sample/` — Hugo 로 만든 레이아웃 시안. 대문에서 링크 |
| Pages | 켜짐. 배포는 커스텀 Actions (`.github/workflows/deploy.yml`) |
| 도메인 | `blog.elkiss.me` — CNAME → `elkiss87.github.io`, DNS only. HTTPS 정상 |
| 스택 | **Hugo 0.164.0 (표준 빌드).** 테마 없이 `layouts/` 직접 |
| 글 | 없음. 시안용 팬그램 문서 한 장뿐 |

**결정된 것**

- public 저장소
- 모바일·데스크톱 양쪽에서 깔끔하게. 한쪽을 우선하지 않는다
- 도메인 하나를 서브도메인으로 나눠 쓴다 (프로필=루트, 블로그=`blog.`)
- **1차는 순수 HTML 로 인프라만 검증한다.** 스택은 그 다음
- 색은 `elkiss.me` 와 같은 값을 쓴다. 서브도메인이라 오가는 사람이 같은 곳으로 느껴야 한다
- **파비콘은 `elkiss.me` 와 같은 아이콘을 쓴다.** 색도 같다 → [LOG.md](LOG.md) 2026-08-07
- **스택은 Hugo.** 테마를 쓰지 않고 마크업을 직접 짠다 → [STACK.md](STACK.md) §7
- **Hugo 버전을 워크플로에 고정한다.** `latest` 로 받지 않는다
- **시안은 대문을 대체하지 않고 `/sample/` 아래에 얹는다.** 시안이 엎어져도 대문은 멀쩡해야 한다
- **글 주소는 `/<파일명>/`.** 번호도 날짜도 넣지 않는다 → 아래 §5
- 사내 코드·시스템 설계는 쓰지 않는다 → 규칙은 `CLAUDE.md`

**아직 결정하지 않은 것**

- 글의 분류 방식 (태그 / 카테고리 / 분류 없음)
- 글을 고쳤을 때 수정일(`lastmod`)을 표시할 것인가 — 실제로 고치게 될 때 정한다.
  `date` 를 안 건드리므로 주소도 순서도 안 바뀐다
- 문법 강조 색 — 지금은 Chroma `github` 스타일. 사이트에 없는 파랑·빨강이 코드에만 들어온다
- 시안을 확정한 뒤 대문을 언제 목록 페이지로 바꿀 것인가
- 댓글, 검색, 방문자 분석
- 코드 라이선스

## 5. 사이트 규칙

고칠 때마다 다시 정하지 않도록 적어둔다. **정해진 만큼만 적는다.**

### 페이지는 셋으로 시작한다

**글 목록 / 글 본문 / 소개.** 이것보다 늘리지 않는다.

- 첫 화면은 **글 목록**이다. 프로필은 `elkiss.me` 가 이미 한다.
  블로그 첫 화면까지 자기소개로 쓰면 같은 말을 두 번 하게 된다
- **소개 페이지는 짧게.** 여기서 뭘 읽을 수 있는지와 프로필 링크까지다
- 태그·아카이브·시리즈는 **글이 쌓여서 목록이 안 읽힐 때** 만든다. 지금은 아니다

### 글

- **날짜를 적는다.** 기술 글은 언제 쓴 것인지가 내용의 일부다
- **분량으로 글을 나누지 않는다.** 한 편에 하나의 이야기가 끝나면 그게 한 편이다
- 회사 이야기는 **일반화해서** 쓴다. 회사를 지우고도 남는 것이 글감이다 → `CLAUDE.md`

### 글 주소 — 2026-08-08 확정

> **`blog.elkiss.me/<파일명>/`**

| | |
|---|---|
| 파일 | `content/posts/<파일명>.md` |
| 주소 | `blog.elkiss.me/<파일명>/` |
| 설정 | `hugo.toml` 의 `[permalinks] posts = '/:contentbasename/'` |

**파일명이 곧 주소다.** 영문 소문자와 하이픈만 쓰고, 제목 번역이 아니라 주제 요약으로
두세 단어. 블로그 전체에서 유일해야 한다. 제목은 한글로 자유롭게 쓴다.

- **번호를 붙이지 않는다.** 순서는 `date` 로 계산되는 값이지 저장할 값이 아니다.
  날짜를 소급해 한 편 끼워 넣으면 뒤 글의 번호가 전부 밀리는데, 그때 다시 매기면
  주소가 깨지고 안 매기면 번호가 거짓말이 된다. **관리할 대상 자체를 만들지 않는다**
- **날짜를 주소에 넣지 않는다.** 고쳐 쓰는 기술 글에서 주소의 날짜는 곧 거짓이 된다.
  날짜는 본문에 표시하고 정렬·RSS 에 쓴다
- **`slug` 를 쓰지 않는다.** `:contentbasename` 은 front matter 의 `slug` 를 무시한다.
  적어두면 안 먹는데 먹는 줄 알게 되니 아예 안 쓴다
- **제목을 고쳐도 주소는 그대로 둔다.** 파일명을 안 건드리면 된다
- 폴더는 `content/posts/` 를 유지하되 주소에는 안 나온다.
  파일 정리와 주소를 분리해두면 나중에 폴더를 나눠도 주소가 안 깨진다

**최상위에 예약된 이름** — 글 파일명으로 쓰면 안 된다.

```
about  posts  tags  categories  page  search  css  sample
index  index.xml  sitemap.xml  robots.txt  404.html  favicon.svg
```

`posts` 는 글 주소를 평평하게 해도 **섹션 목록 페이지로 남는다.** 아카이브가 공짜로 딸려온다.
`page` 는 페이지네이션(`/page/2/`)이 쓴다. 겹치면 Hugo 가 빌드할 때 잡아준다.

### 시안 문서는 글이 아니다

`content/pangram.md` 는 발행할 글이 아니라 **레이아웃을 재는 자다.**
`content/posts/` 밖에 두고 목록·RSS·sitemap 에서 뺐다. 주소(`/pangram/`)로는 열린다.
CSS 를 고칠 때마다 다시 열어보는 용도라 남겨둔다.

### 화면 — 한쪽을 우선하지 않는다

profile-site 는 인스타그램에서 눌러 들어오는 모바일이 실제 방문자라 모바일 우선이 맞았다.
**블로그는 다르다.** 기술 글은 앉아서 읽고, 이력서에 걸 링크라 데스크톱으로 열릴 일도 많다.
어느 쪽도 "되기는 한다" 수준으로 두지 않는다.

- **글 본문의 가독성이 최우선이다.** 폭·줄간격·글자 크기를 먼저 맞춘다.
  한글 본문은 한 줄이 너무 길면 눈이 다음 줄을 놓친다. 데스크톱에서 폭을 제한하는 이유가
  화면이 남아서가 아니라 **길면 읽기 나쁘기 때문**이다
- **코드 블록을 양쪽에서 확인한다.** 기술 블로그에서 제일 자주 깨지는 자리다.
  모바일에서는 가로 스크롤이 본문을 밀지 않아야 하고, 데스크톱에서는 줄바꿈이
  코드를 망가뜨리지 않아야 한다
- 고칠 때는 **좁은 폭과 넓은 폭을 같이 본다.** 한쪽만 보고 고치면 반드시 다른 쪽이 깨진다
- 자바스크립트가 없어도 글은 읽혀야 한다
