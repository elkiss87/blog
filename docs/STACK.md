# 기술 스택

> **결정: Hugo.** 2026-08-08 확정. 근거는 [7. 결정](#7-결정) 에 있다.
> 아래 1~6 은 거기까지 간 검토 과정이다.

profile-site 의 [STACK.md](https://github.com/elkiss87/profile-site/blob/main/docs/STACK.md)
에서 "프레임워크는 블로그에서 고른다" 고 미뤄둔 결정이 이것이다.

---

## 1. 이번엔 빌드가 필요하다

profile-site 는 HTML 파일 하나로 끝냈다. 블로그는 그게 안 된다.

글을 한 편 추가할 때마다 **손으로 고쳐야 하는 것**이 이만큼 생긴다.

- 목록 페이지에 항목 추가
- 날짜순 정렬
- 이전 글 / 다음 글 링크
- 태그를 쓴다면 태그별 페이지
- RSS, `sitemap.xml`

다섯 편까지는 된다. 스무 편이면 안 된다.
빠뜨려도 **에러가 안 나고 조용히 틀린다**는 게 더 나쁘다.

> **글은 마크다운으로 쓰고, HTML은 도구가 만든다.** 이건 확정이다.
> 무슨 도구인지가 남은 문제다.

---

## 2. "빌드를 어디서 하느냐" 는 문제가 아니었다

처음엔 이걸 갈림길로 봤다. 아니다.

**GitHub Actions 가 흡수한다.** 소스만 push 하면 GitHub 쪽 러너가 빌드해서
Pages 에 올린다. public 저장소는 무료고, 어느 도구든 이 방식이 된다.
로컬에서 빌드해 결과물을 커밋하는 방식은 이제 쓸 이유가 없다.

남은 진짜 문제는 **로컬 미리보기**다.

모바일과 데스크톱 양쪽에서 깔끔하게 하려면 폭·줄간격·코드 블록을 눈으로 보면서 고쳐야 한다.
넓혔다 좁혔다 하며 확인해야 하니 확인 횟수도 두 배다.
로컬에서 못 띄우면 `고치고 → push 하고 → 몇십 초 기다려서 → 확인`을 반복하게 된다.
디자인을 다듬는 동안 이건 못 버틴다.

## 3. 판단 기준

| | 기준 | 왜 |
|---|---|---|
| 1 | **로컬 미리보기** | 좁은 화면·넓은 화면을 같이 보면서 고쳐야 한다. 위 2번 |
| 2 | **설치 부담** | 이 머신에 node 도 ruby 도 없다. C++ 로 일하는 사람의 PC 다 |
| 3 | **마크업 통제** | profile-site 처럼 HTML/CSS 를 직접 잡을 수 있어야 한다 |
| 4 | **대중성** | 막혔을 때 검색해서 답이 나와야 한다. 취미로 만드는 사이트다 |
| 5 | **방치 내성** | 몇 달 안 건드리다 돌아왔을 때 그대로 빌드돼야 한다 |

5번을 기준에 넣은 이유가 있다. 개인 블로그는 반드시 몇 달 방치된다.
그때 의존성이 수백 개면 돌아와서 글을 쓰는 게 아니라 **빌드를 고치게 된다.**

## 4. 후보

| 후보 | 런타임 | 설치 | 로컬 미리보기 | 템플릿 |
|---|---|---|---|---|
| **Hugo** | 없음 (Go 단일 바이너리) | exe 하나 | `hugo server` — 저장하면 자동 새로고침 | Go 템플릿 |
| **Zola** | 없음 (Rust 단일 바이너리) | exe 하나 | `zola serve` | Tera (Jinja2 계열) |
| **Astro** | Node | Node + 의존성 수백 개 | `npm run dev` | HTML/JSX 감각 |
| **Eleventy (11ty)** | Node | Node + 의존성 | `npx @11ty/eleventy --serve` | 여러 문법 선택 |
| **Jekyll** | Ruby | Ruby + gem | Ruby 를 깔아야만 됨 | Liquid |
| **직접 스크립트** | 뭐든 필요 | — | 직접 만들어야 함 | 직접 |

### Hugo

Go 로 만들어져 **실행파일 하나**로 끝난다. `winget install Hugo.Hugo.Extended` 면 설치 완료고,
런타임도 패키지 매니저도 딸려오지 않는다. 기준 2·5 를 가장 크게 만족한다.
빌드는 글이 수백 편이어도 1초 안쪽이다.

약점은 **Go 템플릿 문법**이다. `{{ range .Pages }}` 같은 생김새가 처음엔 낯설고,
에러 메시지도 친절한 편이 아니다. 블로그에서 쓰는 문법은 열 개 남짓이라
넘을 수 있는 벽이지만, 없는 벽은 아니다.

진짜 비용은 난이도가 아니라 **조용히 틀린다**는 점이다. `range` 안에서 `.` 이
현재 항목으로 바뀌는데 바깥 값을 그대로 참조하면 에러가 아니라 빈 문자열이 나온다.
목록이 통째로 안 뜨는데 화면은 아무 말도 하지 않는다. `favicon.svg` 슬래시
하나에 걸렸던 것과 같은 종류의 실패다 → [LOG.md](LOG.md) 2026-08-07.

### Zola

**처음 검토에서 빠뜨렸던 후보다.** Rust 로 만든 단일 바이너리라 Hugo 의 장점
(런타임 없음, 빠름, 방치 내성)을 그대로 갖는데, 템플릿이 **Tera** 라 Jinja2 를
아는 사람에겐 Go 템플릿보다 훨씬 읽힌다. taxonomy·페이지네이션·RSS·**검색 인덱스**·
Sass·문법 강조·목차가 전부 바이너리에 들어 있다.

**Hugo 의 유일한 약점을 정확히 겨냥한 물건**이라 진짜 경쟁자였다.
탈락 이유는 기준 4(대중성) 하나다 — 아래 7번.

### Astro

최근 몇 년 콘텐츠 사이트 쪽에서 가장 많이 채택된 도구다.
컴포넌트를 HTML 감각 그대로 짜기 때문에 **마크업 통제(기준 3)가 제일 좋고**,
나중에 글 안에 인터랙티브한 것(데모, 계산기)을 넣고 싶어지면 그때 유리하다.

대신 Node 와 `node_modules` 를 안고 간다. 기준 2·5 에서 밀린다.

### Eleventy

Astro 보다 얇고 HTML 에 가깝다. 통제력은 좋지만 그만큼 **직접 짜야 하는 게 많다.**
초기 세팅에 손이 가고, 정보량은 Hugo·Astro 보다 적다 (기준 4).

### Jekyll

GitHub Pages 에 내장돼 Actions 없이도 배포된다는 게 유일한 장점인데,
2번에서 봤듯 Actions 는 이미 문제가 아니다.
로컬 미리보기를 하려면 결국 Ruby 를 깔아야 하고, 그건 Hugo 보다 훨씬 번거롭다.
생태계도 예전만 못하다. **채택할 이유가 없다.**

### 직접 스크립트

재미는 있는데 유지비를 스스로 진다.
RSS, sitemap, 코드 하이라이팅, 목차 같은 걸 하나씩 다시 만들게 된다.
**블로그를 만들려다 정적 사이트 생성기를 만들게 된다.**

## 7. 결정

> **Hugo. 테마는 쓰지 않고 `layouts/` 를 직접 짠다.** 2026-08-08 확정.

### 왜 Hugo 인가

확정 직전에 2026년 판을 다시 봤다. 정리가 꽤 됐다 — Gatsby 는 끝났고, Next.js 는
풀스택으로 옮겨가 블로그용이 아니게 됐고, Jekyll 은 쇠퇴 중이다.
남은 실질 후보는 **Hugo · Astro · Zola** 셋이었다.

| | Hugo | Astro | Zola |
|---|---|---|---|
| GitHub ★ | **89.4k** | 61.6k | 17.3k |
| 런타임 | 없음 | Node 22.12+ | 없음 |
| 템플릿 | Go 템플릿 | `.astro` | Tera |

**배포는 변별력이 없었다.** 셋 다 Actions 로 빌드해 Pages 에 올리는 방식이 같고
public 저장소라 Actions 시간도 무제한이다. "GitHub 블로그에 뭐가 좋냐" 는 질문으로는
갈리지 않는다. Jekyll 의 기본 내장이 유일한 GitHub 고유 장점인데, 우리는 문서가
도메인에 서비스되는 걸 막으려고 이미 커스텀 Actions 를 쓰기로 했다 → [LOG.md](LOG.md) 2026-08-07.
**우리에겐 이미 없는 장점이다.**

갈린 자리는 둘이었다.

**Astro 를 안 쓴 이유 — 이건 취미 프로젝트다.**
Astro 는 [State of JS 2025](https://2025.stateofjs.com/en-US/libraries/meta-frameworks/) 에서
만족도 5년 연속 1위고 "콘텐츠 사이트" 부문 1위다. 진짜 좋은 도구다.
다만 그 만족도는 **매일 쓰는 개발자** 표본에서 나온다. 매일 쓰면 생태계 유지비가
분산되지만, 두 달에 한 편 쓰는 블로그에서는 글을 쓰러 올 때마다 통째로 청구된다.

추상적인 걱정이 아니다. **Astro 6 이 2026-03-10 에 나오면서 Node 18·20 지원을
끊었다.** Node 22.12 이상이 필수고 Vite 7, Zod 4 로 함께 올라갔다. 2024년에 Astro 로
시작한 사람은 지금 Astro 만이 아니라 **런타임까지** 올려야 한다. 대략 1년에 한 번 온다.

**Zola 를 안 쓴 이유 — 대중성.**
Hugo 에 대한 불만이 Go 템플릿 하나뿐이었는데 Zola 는 그걸 정확히 해결한다.
그런데 17.3k 와 89.4k 는 5배 차이고, 이건 별 개수 자랑이 아니라 **기준 4** 직격이다.
막혔을 때 Hugo 는 포럼 스레드 2만 개 중에 답이 있고 Zola 는 없을 수 있다.

**남는 것.** Go 템플릿 비용은 **뼈대 짤 때 한 번**이다. 그 벽을 넘으면 다시 안 본다.
Zola 는 그 일회성 비용을 깎는 대신 **검색 가능성을 영구히** 깎고,
Astro 는 즐거움을 주는 대신 **유지비를 영구히** 물린다.
셋 중 영구 비용이 없는 것이 Hugo 뿐이다.

> 이 블로그의 병목은 방문자가 아니라 **쓰는 사람의 지속성**이다.
> 글쓰기를 막는 것은 큰 일회성 비용이 아니라 작은 상시 비용이다.

### 왜 테마를 안 쓰는가

1. **디자인이 이미 정해져 있다.** 색·폰트 스택·자간 `.16em`·폭 640px 이
   profile-site 과 맞춰 잡혀 있다. 테마를 쓰면 이걸 남의 CSS 위에 덮어씌우는 일이 되고,
   남의 선택자 특정성과 싸우는 건 빈 파일에서 시작하는 것보다 비싸다
2. **테마는 의존성이고, Hugo 를 고른 이유를 깎는다.** 아래 0.146 개편 때
   여러 테마가 대응 이슈를 열었고, 그 테마 사용자는 자기 사이트가 깨진 채로
   남의 수정을 기다렸다
3. **양이 적다.** [hugo-xmin](https://github.com/yihui/hugo-xmin) 이 HTML 79줄로
   목록·본문·태그·404·RSS 를 다 한다. 뼈대는 큰 공사가 아니다

읽을 것은 hugo-xmin 하나로 충분하다. **설치하지 말고 읽는다.**
PR 목록에 기능이 하나씩 diff 로 쌓여 있어서 "RSS 를 붙이려면 뭐가 필요한가" 를
문서 대신 diff 로 볼 수 있다.

### 반드시 알아야 할 것 — 웹 자료 대부분이 낡았다

**Hugo 0.146.0 에서 템플릿 시스템이 전면 개편됐다.**

| | 예전 (자료 대부분) | 지금 |
|---|---|---|
| 뼈대 | `layouts/_default/baseof.html` | `layouts/baseof.html` |
| 본문 | `layouts/_default/single.html` | `layouts/page.html` |
| 목록 | `layouts/_default/list.html` | `layouts/section.html` |
| 첫 화면 | `layouts/index.html` | `layouts/home.html` |
| 파샬 | `layouts/partials/` | `layouts/_partials/` ← **밑줄** |
| 렌더 훅 | `layouts/_default/_markup/` | `layouts/_markup/` |

`_default/` 가 사라지고 페이지 종류 ↔ 템플릿이 1:1 이 됐다. 하위 호환 매핑이 있어
옛 구조도 대체로 돌지만 공식 구조가 아니다. **2023년 튜토리얼을 따라가면
`_default/` 를 만들게 되고, 나중에 검색한 답과 내 디렉터리가 안 맞는다.**

`hugo new theme` 가 신구조를 생성해준다. 기억으로 짜지 말고 그걸 확인하고 간다.

### 버전과 빌드

- **0.164.0 으로 고정한다.** 워크플로에 버전을 적어두었다. `latest` 로 받으면
  손댄 적 없는 사이트가 어느 날 깨진다. 0.146 이 그 전례다
- **표준 빌드를 쓴다(extended 아님).** 차이는 Sass/SCSS 컴파일 하나인데
  커스텀 프로퍼티를 쓴 순수 CSS 로 가므로 필요 없다.
  로컬에 extended 를 깔아도 표준으로 짠 사이트는 그대로 빌드된다. 반대만 안 된다
- `locale` 을 쓴다. `languageCode` 는 0.158 에서 deprecated 됐다

### 나중에 뒤집게 된다면

- 글에 **인터랙티브한 것**(계산기, 시각화)을 진짜로 넣고 싶어지면 Astro
- Go 템플릿을 실제로 만져보고 도저히 못 견디겠으면 Zola

둘 다 마크다운 본문은 그대로 옮겨간다. **글이 인질로 잡히지는 않는다.**
